# 电视麦克风测试

独立诊断应用 `local.mytv.mictest`，用于验证普通应用能否从电视内置麦克风或小米语音遥控器录音。没有网络权限，不包含英语识别、发音评分或后台录音服务。

## 构建与安装

在仓库根目录运行：

```powershell
.\build.ps1 -App mictest
adb -s 192.168.1.132:5555 install -r apps/mictest/build/mictest.apk
adb -s 192.168.1.132:5555 shell am start -n local.mytv.mictest/.MicTestActivity
```

首次开始录音时允许麦克风权限。遥控器方向键选择按钮，确认键操作。

## 测试方法

先暂停电视播放，避免扬声器声音影响判断。

1. 点“输入”切换到“电视内置麦克风”，音源选 MIC。点开始，在电视前读 `I like reading English books.`，等待 12 秒或主动停止，然后回放。
2. 切换到 `MIBT.VoiceControl` 输入，重复测试。先不按语音键，再开始新一轮录音并按住实体遥控器语音键朗读。
3. 如果没有音频，切换音源到 VOICE_RECOGNITION 再试。更换输入前须结束录音。
4. 对照“实际输入”判断路由；首选请求被接受也不保证实际使用该设备。非零音量可能只是噪声，须回放确认清晰人声。

语音键可能唤起小爱并占用麦克风，甚至覆盖测试应用。应用离开可见状态会停止录音；日志会记录这一情况。这只能说明该操作流程被打断，不能据此断言遥控器硬件不支持。

录音为 16kHz、单声道、16-bit PCM WAV，保存在应用私有目录 `files/last-recording.wav`，每次开始录音覆盖上次内容；卸载会删除。录音在工作线程执行，最多 12 秒；退出界面停止录音和回放。

```powershell
adb -s 192.168.1.132:5555 logcat -d -s MicTest:I
adb -s 192.168.1.132:5555 uninstall local.mytv.mictest
```

## 2026-11-06 初步实测

设备 MiTV-MFTR0，Android 14。APK 构建、签名验证、安装与界面检查通过。

- 系统公开了内置输入 `#8`（type 15）和 `MIBT.VoiceControl #18`（type 3）。
- MIC + 内置输入：实际路由为 #8，录到约 11.98 秒，峰值 41 / RMS 2（16-bit PCM 幅值）。说明录音链路有数据，尚未现场朗读确认人声和距离。
- MIC + 遥控器输入：首选请求被接受，实际路由为 #18，12 秒内未收到采样。此次未按住实体遥控器语音键，不能作为遥控器最终不可用的结论。
- VOICE_RECOGNITION + 遥控器输入：同样实际路由 #18，12 秒未收到采样。
- VOICE_RECOGNITION + 内置输入：实际路由 #8，录到约 11.98 秒，峰值 10 / RMS 2，同样还需现场朗读确认。

尚需现场完成两种输入的英语朗读、回放和实体语音键测试。本应用不评估发音。

### 现场反馈补充

用户确认：当前界面的“系统默认输入 + VOICE_RECOGNITION”在按住实体遥控器麦克风键时能录音，其他组合未取得可用朗读录音；长按该键同时会唤起小爱同学。此前内置输入返回非零数据，仅证明存在采样，不能认定内置麦克风能正常收集人声。

下一项待验证的是：拦截语音键的小爱唤起行为后，遥控器是否仍会发送音频。两者可能共用系统处理路径，不能预先保证可以分开。暂未禁用小爱或修改系统语音设置。

## 语音键拦截实验版

启动默认使用“系统默认输入 + VOICE_RECOGNITION”。最新本机构建默认关闭“语音键拦截实验”，打开“自动收起小爱”；两个开关相互独立。需要启用本应用的“麦克风测试语音键拦截”无障碍服务；未连接时会阻止启动实验录音，避免把未生效的操作误当成实验结果。此前已在测试电视通过 ADB 添加并确认连接，保留了原有小爱无障碍服务，没有禁用小爱应用；升级或电视重启后需再确认服务状态。

1. 保持拦截实验为“开”，点开始录音，再按住实体遥控器语音键朗读；须在 12 秒内完成。
2. 观察小爱是否出现，录音结束后查看“拦截次数”和最后收到的按键，再回放。
3. 将拦截实验设为“关”，重复相同操作，作为对照。

只过滤录音期间的 VOICE_ASSIST、ASSIST、SEARCH 按键，以及本机小米遥控器（vendor 0x2717 / product 0x32b8）上 UNKNOWN + 扫描码 63 的按键；其他键放行。若语音键在录音期间被拦截，松开事件也会被成对拦截，即使松开时录音已经结束。结束录音、离开界面后不会拦截新的按键。服务不读取界面内容，仅记录录音测试期间的按键码、设备标识及窗口切换的应用包名用于诊断。

判断方法：

- 拦截次数增加、小爱不出现且回放有人声：可继续采用此方案。
- 拦截次数增加、小爱不出现但无音频：语音启动可能依赖被拦截的系统流程。
- 拦截次数为 0、小爱仍出现：语音键未进入本服务，需根据日志继续判断厂商处理路径。
- 拦截次数增加、小爱仍出现：小爱可能还通过另外的厂商事件启动，单纯按键过滤不足。

当前仅验证了构建、签名、安装、服务连接（flags=32）。ADB 模拟 VOICE_ASSIST 长按没有进入过滤回调，不能代替实体遥控器测试；尚未确认拦截小爱成功。

首次实体测试显示拦截次数为 0。日志实际收到 UNKNOWN / scan=63 的按下和松开，随后小爱出现；录音实际路由 #18，取得约 3.69 秒音频，峰值 9152 / RMS 995。因此服务确实收到了按键，但第一版的标准语音键匹配未覆盖此厂商映射。现已加入上述特定遥控器扫描码匹配，待第二次实体测试验证小爱是否被阻止以及录音能否继续。

第二次实体测试已确认：按下与松开均进入过滤回调并返回拦截，但小爱仍出现。日志在 22:57:33.617 记录 scan=63 已拦截，22:57:34.307 记录小爱窗口；最终录到约 3.03 秒音频，峰值 6918 / RMS 509。结论是这台固件上的无障碍按键过滤不足以阻止小爱启动，具体其他启动路径尚未确定。

2026-11-07 部署更新：已重新构建、通过签名验证并覆盖安装到 MiTV-MFTR0；无障碍服务连接成功（flags=32），截图确认默认输入、VOICE_RECOGNITION、关闭按键拦截、开启自动收起小爱。应用已打开，尚待实体语音键和回放验证。

新实验在录音期间观察到 `com.xiaomi.voicecontrol` 的窗口后，等待 350ms，再核对最后一次窗口事件仍属于小爱，然后通过无障碍发送一次系统返回。每轮录音最多尝试一次；结束录音、离开测试界面会取消未执行的动作。不会禁用小爱、修改蓝牙服务或在其他应用使用期间自动返回。这是在小爱启动后尝试收起界面的实验，不能保证录音通道保持开启。

安装最新 `apps/mictest/build/mictest.apk` 后按下列步骤测试：

1. 保持默认输入和 VOICE_RECOGNITION，语音键拦截关闭、自动收起小爱开启。确认无障碍服务已连接。
2. 点开始录音，按住语音键不松手，连续朗读整句，特别注意小爱收起前后的声音。
3. 查看“收起实验”状态，回放确认后半句是否还在。返回操作成功仅表示系统接受请求，须现场确认界面是否收起。
4. 关闭“自动收起小爱”，重新录制同一句作为对照。

如果小爱收起后音频立刻停止，该流程不适合正式答题；如果持续录音且界面恢复，再评估是否值得接入。拦截键和收起界面两条路径均无效时，应改测独立音频输入，而非继续依赖按住小爱语音键。

### 2026-11-07 实体测试日志结果

- 09:01 轮次（按键拦截开、自动收起开）：09:01:45.068 发送返回，45.599 回到测试 App；45.961 至 48.497 仍有非零音频，48.764 记录实体语音键松开。最终取得 4.635 秒音频，峰值 14712 / RMS 1586，回放完成。这说明至少这一次收起小爱后录音链路未立即停止。
- 09:02 轮次（按键拦截关、自动收起开）：09:02:18.173 发送返回，18.699 回到测试 App，19.581 至 20.596 仍有音频；后续 23.181 和 26.849 再次出现小爱窗口。本版每轮只发送一次返回，因此未再次收起。12 秒测试窗口内共取得 6.2775 秒音频，峰值 12860 / RMS 1979，回放完成。

阶段结论：自动收起后继续录音的路径已有实机日志支持，尚不能认定正式可用。仍需用户确认回放中朗读是否完整，以及再次出现的小爱窗口的实际表现。录音秒数是收到的 PCM 采样时长，不代表整个测试窗口连续收音；等待输入的时间不会写成静音样本。
